# CodeCockpit Remote Protocol

Version 1 — the contract between the CodeCockpit desktop app (the server) and a
remote client, e.g. the Android app (the phone). All messages are JSON text frames
over a TLS WebSocket.

- Endpoint: `wss://<desktop-ip>:<port>` (default port **47315**, configurable in Settings)
- Transport: HTTPS with a **self-signed certificate** generated by the desktop on
  first start. The client must either pin the certificate fingerprint shown in the
  desktop's Settings → Remote access tab (TOFU: compare once on first connect, then
  trust) or accept it after explicit user confirmation.
- One WebSocket per client. The server allows at most **4 authenticated clients**
  simultaneously. Connections that never authenticate within **10 seconds** are
  closed. After **5 failed auth attempts** an IP is banned for **60 seconds**.
- **Which address to use** — the protocol is identical on every path; the desktop
  shows copyable addresses in Settings → Remote access:
  - *Same network*: a LAN address of the desktop, or its Tailscale address
    (100.64/10) when both devices are on the same tailnet.
  - *IPv6 direct*: the desktop's public IPv6 address (Settings shows it only when
    the network provides one), dialed as `[ipv6-addr]:port`. Works from another
    network whenever both ends have public IPv6 and no gateway on the path blocks
    inbound IPv6 (some home gateways do by default). The listener is dual-stack:
    the same port serves IPv4 and IPv6. Tunneling tools (Tailscale, ZeroTier,
    plain WireGuard, frp, …) work equally well — they just hand the phone another
    reachable address.

## Authentication

The first frame a client sends must be an `auth` request (anything else gets
`error` and the connection is closed after the timeout).

### First pairing (shared secret)

```json
C → S  { "type": "auth", "secret": "<pairing secret>", "name": "Pixel 9" }
S → C  { "type": "auth_ok", "token": "<device token>", "fp": "<cert fingerprint>" }
```

- The pairing secret is shown (and copyable) in Settings → Remote access.
- On success the server mints a **device token** (random 32 bytes, hex) and stores
  only its SHA-256 hash. The token is sent to the client **exactly once**; the
  client must persist it for reconnects.
- `fp` is the SHA-256 of the desktop's TLS certificate, grouped in 8 hex blocks
  for human comparison against what the client displays.

### Reconnect (device token)

```json
C → S  { "type": "auth", "token": "<device token>" }
S → C  { "type": "auth_ok", "token": "", "fp": "<cert fingerprint>" }
```

`token` is empty on token-based auth (the client already has it).

### Failures

```json
S → C  { "type": "auth_fail", "reason": "bad_secret" | "bad_token" | "banned" | "too_many_clients" }
```

The connection is closed after every `auth_fail`.

Regenerating the secret in Settings un-pairs all devices (their tokens stop
working). Revoking a device closes its live connections immediately.

## Requests (client → server)

| type     | fields                | effect |
|----------|-----------------------|--------|
| `auth`   | `secret`+`name` or `token` | authenticate (above) |
| `list`   | —                     | full session list → `sessions` |
| `attach` | `id` (session id)     | start streaming this session → immediate `conv_snapshot` (+ `status` if known) |
| `detach` | `id`                  | stop streaming that session |
| `input`  | `id`, `data`          | write `data` into the session's terminal (a submitted prompt) |
| `mode`   | `id`, `mode`          | switch permission mode: `default` \| `acceptEdits` \| `plan` \| `bypassPermissions` |
| `create` | `cwd`, `mode`, `engine?`, `title?`, `resumeId?` | launch a new session (`resumeId` = engine-native id to resume from history) → `session_created` + `sessions` broadcast. A nonexistent `cwd` is **rejected** with an `error`, never silently replaced |
| `kill`   | `id`                  | terminate the session process → `exit` event + `sessions` broadcast |
| `rename` | `id`, `title`         | set a custom title (applies to the session's engine-native id) → `sessions` broadcast |
| `history` | `engine?`, `limit?`  | engine-native session history (default claude, cap ~100) → `history` |
| `delete_history` | `id`, `engine?` | permanently delete one history entry → fresh `history` for that engine |
| `ping`   | —                     | → `pong` (keepalive) |

`input`, `mode`, `kill` and `rename` are only valid for sessions owned by the
desktop app (the ids from `sessions`), never for arbitrary engine sessions found
on disk.

### Remote session management — security model

Pairing grants **full control** of the desktop's engine sessions: `create`
launches a real CLI process in any directory that exists on the desktop, `kill`
terminates one, and history deletion is permanent. This is by design — the
pairing secret is entered by the desktop's owner on the phone, and possession of
a valid token implies that trust. Protect the pairing secret; anyone holding it
can do everything the desktop can.

## Events (server → client)

Events with an `id` are delivered **only to clients attached to that session**.
Message arrays follow the `RemoteMessage` shape below.

| type            | fields                              | meaning |
|-----------------|-------------------------------------|---------|
| `sessions`      | `sessions: SessionSummary[]`        | answer to `list` |
| `conv_snapshot` | `id`, `messages: RemoteMessage[]`   | full buffered conversation at attach time |
| `conv_append`   | `id`, `messages: RemoteMessage[]`   | new/updated messages; **upsert by `id`** (a re-sent id replaces the earlier entry — streaming updates mutate rows in place) |
| `busy`          | `id`, `busy: boolean`, `bg: number` | work-state changed; `bg` = running background shells. Also triggers a `sessions` broadcast so every client's sidebar stays in sync |
| `status`        | `id`, `status: SessionStatus`       | telemetry snapshot (tokens, cost, model, …); `todos` carries the latest plan list when the agent published one |
| `exit`          | `id`, `code: number`                | session process exited |
| `session_id`    | `id`, `claudeSessionId: string`     | engine reported its native session id |
| `session_created` | `id`                              | answer to `create`; the new session also arrives via the `sessions` broadcast |
| `history`       | `engine`, `sessions: NativeSessionInfo[]` | engine-native history (resume candidates + deletable entries) |
| `pong`          | —                                   | keepalive answer |
| `error`         | `message: string`                   | malformed request / failed input, mode change or create |

## Shapes

### SessionSummary

```json
{
  "id": "uuid",                       // desktop session id (use for attach/input/mode)
  "engine": "claude" | "codex" | "opencode",
  "title": "Refactor auth",
  "cwd": "D:/work/app",
  "claudeSessionId": "uuid-or-null",  // engine-native session id
  "status": "running" | "exited",
  "permissionMode": "default",
  "startedAt": 1731400000000,
  "busy": false,
  "bg": 0,
  "model": "claude-sonnet-4-5",
  "tokensIn": 12345,
  "tokensOut": 678,
  "costUsd": 0.12,
  "turns": 3
}
```

### RemoteMessage

```json
{
  "id": "stable-id",        // unique per session; upsert key for conv_append
  "ts": 1731400000000,      // epoch ms
  "role": "user" | "assistant" | "tool",
  "text": "…",              // chat content (user prompts / assistant replies); absent on tool entries
  "toolName": "Bash",       // tool entries only
  "toolInput": "{…}",       // full tool arguments, clamped to ~4000 chars
  "toolOutput": "…",        // tool result text, clamped to ~4000 chars; upserted onto the tool entry when the engine reports the result
  "tokensIn": 123,          // per-message usage when the engine reports it
  "tokensOut": 45,
  "costUsd": 0.01
}
```

`text`, `toolName`, `toolInput`, `toolOutput`, and the usage fields are optional
depending on role/engine.

### NativeSessionInfo

```json
{
  "sessionId": "uuid",        // engine-native id — the resumeId for `create`
  "cwd": "D:/work/app",
  "title": "Refactor auth",
  "permissionMode": "default",
  "lastTs": 1731400000000,
  "sizeBytes": 45678,
  "projectEncoded": "…",
  "engine": "claude",
  "custom": false
}
```

### SessionStatus

`model: string`, `tool: string|null`, `toolDetail: string`, `tokensIn/tokensOut/
cacheRead/cacheWrite: number`, `costUsd: number`, `turns: number`,
`toolCalls: number`, `toolCounts: Record<string, number>`, `durationMs: number`,
`lastActivity: number`, `eventCount: number`, `backgroundTasks: number`,
`todos?: TodoItem[]` — latest plan list (`{content, status: pending|in_progress|
completed, activeForm?}`), populated by claude TodoWrite / codex update_plan /
openCode todowrite; absent until the agent first publishes a plan.

## Client behavior notes

- **Upsert**: store messages in a map keyed by `id`; `conv_append` may re-deliver
  an existing id with newer content (streaming). Render in `ts` order.
- **Reconnect**: on disconnect, reconnect + `auth` with the stored token, then
  re-`attach` to the sessions being viewed; render the fresh `conv_snapshot`.
- **Buffers are bounded**: the desktop keeps the last ~500 messages per session.
  Full history of exited sessions is not (yet) available remotely.
- Engine prompt scaffolding (`<user_instructions>`, `<environment_context>`, …)
  is already filtered server-side; clients never see it.
